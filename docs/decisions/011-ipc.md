# 011. Связь CLI с открытым редактором (проба 1.11)

Дата: 2026-10-28. Код пробы: `spikes/ipc`. interprocess 2.4.7, local socket (на Windows — именованный канал), имя в пространстве `GenericNamespaced`.

## Результаты

- **Редактор не запущен:** `Stream::connect` сразу (< 0,1 мс) возвращает `NotFound`. CLI внятно сообщает об этом и переходит на прямую правку файлов (решение ARCHITECTURE №6).
- **Редактор запущен:** 100 команд по одной, JSON-строки.
  - Задержка от отправки до подтверждения «кадр с новым значением построен»: p50 0,2 мс, p95 0,3 мс, максимум 0,4 мс.
  - На экран кадр попадает на один vsync позже (≤ 17 мс при 60 Гц). Требование «быстрее 100 мс» выполнено с запасом.
- **Визуально:** после 43 команд окно показывает «Значение из CLI: 420» — последнюю команду (42 × 10).

## Решение

- Сервер в редакторе: поток с `ListenerOptions::create_sync()`, на каждое подключение свой поток.
- Команда уходит в UI через канал, после чего вызывается `ctx.request_repaint()`. UI применяет команду в `logic()` (через реестр команд и с записью в историю) и отвечает клиенту после кадра.
- Протокол продукта: JSON-сообщения с длиной в начале (в пробе — строки JSON, их проще отлаживать). Ответ содержит однострочный diff или ошибку с подсказкой — тот же формат, что у CLI без редактора.
- Имя канала включает имя пользователя: `devcast-<user>`. Тогда два пользователя на одной машине не мешают друг другу.
- Если редактор держит проект открытым, CLI пишет только через него (lock-файл говорит, кто держит проект).

## Задача 3.15: управление записью из CLI (2026-10-28)

- `devcast record` — сам процесс записи: создаёт проект и пишет до стопа. Другие вызовы `devcast record stop|pause|resume|cancel` доходят до него по local socket `devcast-record-<пользователь>` (`dc-ipc`, сообщение — u32 длины + JSON, одно подключение — запрос и ответ).
- Канал занимается **до старта захвата**: второй `devcast record` сразу получает «запись уже идёт», а запросы, пришедшие, пока запись стартует (выбор кодека ~1 с), ждут в очереди и выполняются сразу после старта. Ответ приходит, когда запись выполнила команду: `record stop` печатает созданный проект.
- Никто не слушает — `record stop` сразу отвечает «запись не идёт» (код 1). Ожиданий, опросов файлов и `sleep` нет: процесс записи ждёт запрос на канале (`recv_timeout` до конца `--duration`).
- После стопа поток канала будится подключением к себе (`Listener::wake`) и завершается; ошибки отдельных запросов идут предупреждениями в stderr процесса записи.
