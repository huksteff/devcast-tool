# 011. Связь CLI с открытым редактором (проба 1.11)

Дата: 2026-10-28. Код пробы: `spikes/ipc`. interprocess 2.4.7, local socket (на Windows — именованный канал), имя в пространстве `GenericNamespaced`.

## Результаты

- **Редактор не запущен:** `Stream::connect` сразу (< 0,1 мс) возвращает `NotFound`. CLI внятно сообщает об этом и переходит на прямую правку файлов (решение ARCHITECTURE №6).
- **Редактор запущен:** 100 команд по одной, JSON-строки.
  - Задержка от отправки до подтверждения «кадр с новым значением построен»: p50 0,2 мс, p95 0,3 мс, максимум 0,4 мс.
  - На экран кадр попадает на один vsync позже (≤ 17 мс при 60 Гц). Требование «быстрее 100 мс» выполнено с запасом.
- **Визуально:** после 43 команд окно показывает «Значение из CLI: 420» — последнюю команду (42 × 10).

## Решение

- Сервер в редакторе: поток с `ListenerOptions::create_sync()`, на каждое подключение свой поток.
- Команда уходит в UI через канал, после чего вызывается `ctx.request_repaint()`. UI применяет команду в `logic()` (через реестр команд и с записью в историю) и отвечает клиенту после кадра.
- Протокол продукта: JSON-сообщения с длиной в начале (в пробе — строки JSON, их проще отлаживать). Ответ содержит однострочный diff или ошибку с подсказкой — тот же формат, что у CLI без редактора.
- Имя канала включает имя пользователя: `devcast-<user>`. Тогда два пользователя на одной машине не мешают друг другу.
- Если редактор держит проект открытым, CLI пишет только через него (lock-файл говорит, кто держит проект).

## Задача 3.15: управление записью из CLI (2026-10-28)

- `devcast record` — сам процесс записи: создаёт проект и пишет до стопа. Другие вызовы `devcast record stop|pause|resume|cancel` доходят до него по local socket `devcast-record-<пользователь>` (`dc-ipc`, сообщение — u32 длины + JSON, одно подключение — запрос и ответ).
- Канал занимается **до старта захвата**: второй `devcast record` сразу получает «запись уже идёт», а запросы, пришедшие, пока запись стартует (выбор кодека ~1 с), ждут в очереди и выполняются сразу после старта. Ответ приходит, когда запись выполнила команду: `record stop` печатает созданный проект.
- Никто не слушает — `record stop` сразу отвечает «запись не идёт» (код 1). Ожиданий, опросов файлов и `sleep` нет: процесс записи ждёт запрос на канале (`recv_timeout` до конца `--duration`).
- После стопа поток канала будится подключением к себе (`Listener::wake`) и завершается; ошибки отдельных запросов идут предупреждениями в stderr процесса записи.

## Задача 5.14: очередь экспорта между вызовами CLI (2026-10-29)

- **Статус живёт в процессе очереди, не в файле.** Первый `devcast export` занимает канал `devcast-export-<пользователь>` и запускает `dc_encode::ExportQueue` (один поток, задания по порядку). Следующие вызовы (из любой папки и проекта) шлют туда `Run` со снимком рабочего состояния проекта и ждут ответа на том же соединении — он приходит, когда готов их файл. Процесс очереди живёт, пока очередь не опустеет, потом освобождает канал.
- `export status` и `export cancel [eN]` — запросы `Status` и `Cancel` в тот же канал; никто не слушает — «экспорт не идёт» (status, код 0) или «отменять нечего» (cancel, код 1). Файла статуса в `cache/` нет: он врал бы после убитого процесса, а канал отвечает только живой очередью.
- Снимок проекта берётся в момент вызова: правки после `export` в этот файл не попадают — можно монтировать дальше.
- Гонка «очередь закрывается, а новый вызов как раз подключился» даёт ошибку «очередь только что закрылась: начни экспорт ещё раз» — без ожиданий и повторов.
- Замер (release, RTX 3060 Ti, NVENC): запись `speech.devcast` 20 с → 1080p60 высокое — 4,2 с через CLI (×4,8 реального времени, 31,3 МБ); через API 323 кадра/с, ×5,4; низкое — 399 кадров/с, 13,5 МБ; 4K60 — 130 кадров/с, ×2,2, 77,6 МБ; GIF 720p 15 fps — 3,7 с, 5,3 МБ.

## Задача 7.32: CLI правит проект открытого редактора (2026-11-02)

- Канал — тот же `devcast-app-<пользователь>`, что у единственного экземпляра; протокол `dc_ops::live` (`Show`, `Open`, `Write`, `Save`). Поток канала передаёт запрос главному окну (`Call`, будит только ROOT) и ждёт его ответа.
- CLI спрашивает редактор, только если `lock-owner.json` называет программу (`LOCK_OWNER`); программы нет или проект не у неё — обычный путь по файлам.
- **Команды не пересылаются, пересылается результат.** Многие правки CLI — не шаги реестра (`style copy`, `set`, `clip add` после копии файла, `cut w12-w20`, `zoom add --at clicks`, undo/redo), их не собрать в редакторе. Поэтому `Open`: редактор пишет рабочее состояние (`Document::flush`) и отдаёт ревизию; CLI открывает его с диска и выполняет команду тем же кодом, что без редактора (ответы, ошибки, `--dry-run` одинаковые); события истории (`Do(Change)`, `Undo`, `Redo`) уходят в `Write`. Редактор берёт их (`live::replay`, `History::push`), только если ревизия та же — состояние совпадает, результат равен посчитанному CLI; иначе отказ «проект изменился в редакторе…». Ни ожиданий, ни повторов.
- Команды чтения (`ls`, `frame`, `export`, `history` …) тоже идут через `Open`: видят несохранённое редактора.
- Изменение из CLI в редакторе несохранённо до Ctrl+S, как своё; `devcast save` — `Save` (Ctrl+S редактора).
