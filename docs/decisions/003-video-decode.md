# 003. Декодирование и показ видео (проба 1.3)

Дата: 2026-10-28. Код пробы: `spikes/video`.
Проверено на Windows 11, NVIDIA RTX 3060 Ti. Тестовые ролики сделаны генератором `testsrc2` + `h264_nvenc`.

## Сборка с FFmpeg

- **FFmpeg 9.0, shared, GPL** — сборка BtbN `ffmpeg-n9.0-latest-win64-gpl-shared-9.0.zip`, SHA-256 архива `e9cc7f09…185ff`. Есть кодеки `h264_nvenc`, `h264_amf`, `h264_qsv`, `h264_mf`, `libx264`. DLL: avcodec-63, avformat-63, avutil-61, avfilter-12, avdevice-63, swscale-10, swresample-7.
- **libclang** нужен только при сборке (bindgen). Хватает одного `libclang.dll` из официального колеса PyPI `libclang 18.1.1` (SHA-256 колеса `4dd2d3b8…f7fb`), полный LLVM не нужен.
- **Rust:** `ffmpeg-next 9` / `ffmpeg-sys-next 9.0.1` (поддерживают FFmpeg до 9.0). Пути передаются через `.cargo/config.toml` `[env]`: `FFMPEG_DIR`, `LIBCLANG_PATH` (относительно, на `.deps/`).
- **Запуск:** DLL FFmpeg должны лежать рядом с exe или в PATH.
- Сборка `latest` у BtbN меняется каждый день. Для воспроизводимости `xtask deps` должен качать сборку с датированным тегом и проверять SHA-256 (задача 2.0).

## Результаты

| Что | 1080p60 | 4K30 |
|---|---|---|
| Программное декодирование (frame threads), без окна | 410 к/с | 92 к/с |
| D3D11VA + копирование кадра в память CPU | 122 к/с | 40 к/с |
| Точная перемотка, GOP 2 с, программно (среднее / p95) | 100 / 163 мс | 285 / 456 мс |
| Точная перемотка, GOP 1 с, программно | 55 / 84 мс | 218 / 297 мс |
| Точная перемотка, GOP 1 с, D3D11VA | 55 / 99 мс | 109 / 189 мс |
| Ошибка кадра после перемотки (200 перемоток) | 0 | 0 |
| Воспроизведение в окне egui 6 с: показано / пропущено | 358 / 2 | 180 / 0 (D3D11VA: 179 / 1) |
| CPU при воспроизведении | 51% ядра | 123% (D3D11VA: 75%) |

- **Показ.** Две текстуры (Y как `R8Unorm`, UV как `Rg8Unorm`), WGSL переводит BT.709 limited range → RGB в `egui_wgpu::Callback`. Формат поверхности egui — `Bgra8Unorm` (не sRGB). Шейдер учитывает и sRGB-поверхность через override-константу. Цвета тестовых полос на скриншоте верные.
- **Точная перемотка:** seek назад к ключевому кадру, затем декодирование вперёд **без копирования промежуточных кадров** (копирование всех кадров делало перемотку в 1,7 раза медленнее).

## Решение

- **Декодирование по умолчанию программное**, с потоками на кадры. Оно быстрее D3D11VA с копированием и проще.
- **Аппаратное декодирование** нужно только для экономии CPU на 4K. Подключаем его вместе с передачей кадра в wgpu без копирования (D3D11 → wgpu), отдельной задачей при оптимизации (7.34), если CPU окажется проблемой.
- **Наши записи пишутся с GOP 1 с** (было 2 с), тогда точная перемотка 1080p укладывается в 100 мс. В задачах 3.4 и ARCHITECTURE «GOP 2 с» заменяется на «GOP 1 с».
- **Перемотка в редакторе** (задача 4.3 / 7.5):
  - пока пользователь тянет указатель, показываем ближайший ключевой кадр (быстро);
  - на отпускании — точный кадр;
  - кэш кадров вокруг указателя.
- **Реализация (4.3, `dc_media::Decoder`), замер 2026-10-28 на ПК владельца, 100 случайных перемоток (`seek_timing`):** 1080p60 GOP 1 с (testsrc2, x264) — точная 30 / 49 мс (среднее / p95), к ключевому кадру 14 / 20 мс; запись speech 720p — точная 41 / 80 мс, к ключевому 12,5 / 14 мс. Пул держит один кадр NV12: 3,1 МБ на 1080p, 1,4 МБ на 720p. Точный кадр совпал с FFmpeg побайтно на 50 случайных позициях в mp4/mov/mkv (B-кадры)/webm и с переменной частотой.
- **Импортированные видео с длинным GOP** перематываются медленнее — это известное ограничение.
- **Единичные пропуски кадров** при воспроизведении убираются в 7.5: там часы будут от звукового выхода и с выравниванием по vsync.
