# 006. Экспорт в MP4 (проба 1.6)

Дата: 2026-10-28. Код пробы: `spikes/export`. RTX 3060 Ti, FFmpeg 9.0 (BtbN gpl-shared), ffmpeg-next 9.

## Цепочка

1. Рендер кадра на GPU (wgpu, `Rgba8UnormSrgb`).
2. Перевод в NV12 на GPU двумя проходами: Y — полное разрешение `R8Unorm`, UV — половина `Rg8Unorm`. Билинейная выборка в центре блока 2×2 усредняет блок. Формулы BT.709 limited range, перед ними перевод в гамма-кодированный цвет.
3. Чтение кадра на CPU через кольцо из 4 буферов, чтобы GPU не простаивал.
4. FFmpeg H.264, AAC 48 кГц стерео 192 кбит/с, mp4.

## Самопроверка кодеков

Кодек кодирует 10 серых кадров 640×360, программный декодер их раскодирует, яркость должна быть около 128.

| Кодек | Результат на этой машине |
|---|---|
| h264_nvenc | OK, 128.0, ~150 мс |
| h264_qsv | ошибка открытия (нет Intel GPU) — правильно отбракован |
| h264_amf | ошибка открытия (нет AMD GPU) — правильно отбракован |
| h264_mf | OK, 128.0, ~66 мс |
| libx264 | OK, 128.0, ~12 мс |

## Скорость (10 с тестового ролика: рендер, NV12, чтение, кодирование, звук, mp4)

| | NVENC | MediaFoundation | libx264 (veryfast, crf 20) |
|---|---|---|---|
| 1080p60 | 415 fps, ×6,9 реального времени | 364 fps, ×6,1 | 349 fps, ×5,8 |
| 4K30 | 113 fps, ×3,8 | 94 fps, ×3,1 | 88 fps, ×2,9 |

- Файл проверен через ffprobe: h264 1920×1080 60/1, 600 кадров; aac 48 кГц 2 канала; длительность 10,005 с. Кадр на 2-й секунде верный (ffmpeg → PNG, проверено глазами). Звук: среднее −17 dB.
- libx264 на тестовой сцене быстрый, потому что сцена простая. На настоящей записи экрана CPU-кодек будет заметно медленнее. Сравнение с v1 на реальной записи — в задаче 5.41.

## Решение

- **Порядок кодеков**:
  - по производителю GPU: NVIDIA → `h264_nvenc`, Intel → `h264_qsv`, AMD → `h264_amf`;
  - затем `h264_mf`;
  - затем `libx264`.

  Каждый — только после успешной самопроверки. Результат самопроверки кэшируется на запуск приложения.
- **Конвертация RGB → NV12 на GPU**, на CPU только копирование готовых плоскостей.
- **Цветовые метки в выходном файле обязательны**: `color_range = tv`, `colorspace / color_primaries / color_trc = bt709`. В пробе они не заданы (ffprobe показывает `unknown`), и плееры могут угадать неверно.
- **Важная деталь wgpu**: проход, который пишет в текстуру, не должен держать её же в bind group на чтение (ошибка конфликта использования). У каждого прохода своя привязка.
- Аппаратное кодирование при записи (3.4) использует тот же список и ту же самопроверку.

## Уточнение в 3.4: порядок без определения производителя

При записи кадры попадают в кодек из памяти CPU, поэтому видеокарта захвата и кодирования не обязаны совпадать. Порядок фиксированный: `h264_nvenc` → `h264_qsv` → `h264_amf` → `h264_mf` → `libx264`. Аппаратный кодек чужого производителя не проходит самопроверку (ошибка открытия, миллисекунды), так что на ПК с одной видеокартой результат тот же, что «по производителю», а на ноутбуке с двумя первой идёт дискретная NVIDIA.

Самопроверка дополнительно требует ключевые кадры там, где их попросили (после паузы в слотах), иначе GOP 1 с не гарантирован. Затем проверка скорости: секунда тестовой картинки на настоящем размере и fps, нужно ≥ fps × 1,25; кто не успевает, уступает следующему, а если не успел никто — ошибка `TooSlow` до старта с советом снизить fps или размер.

## Уточнение в 5.3: положение цветности

Наши записи помечены `chroma_location=left` (как H.264 по умолчанию), и видеопроход (5.3) читает цветность слева: отсчёт цветности стоит на чётном столбце яркости, по вертикали — между строками. Проверено: кадр записи совпадает с `ffmpeg scale in_chroma_loc=left` до ±1 на канал, а с `center` расходится до 89 на резких цветовых границах. Перевод в NV12 при экспорте (5.12) должен ставить цветность так же (по горизонтали — столбцы 2i, по вертикали — среднее строк), либо честно пометить файл `chroma_location=center`, если блок 2×2 усредняется по центру, как в пробе. Иначе цвет на границах сдвинется на полпикселя.

## Задача 5.12: экспорт MP4 (2026-10-29)

- **Звук — AAC LC 48 кГц стерео 192 кбит/с**, как в пробе. Новое решение не нужно: AAC в MP4 играют все плееры, браузеры и мессенджеры (Telegram, Slack, WhatsApp), а FLAC в MP4 — нет. Задержку кодера (1024 сэмпла) прячет edit list: ffprobe видит начало звука в 0 и длительность звука = длительности проекта (±2 мс, тест).
- **Цветность** при переводе в NV12 ставится слева, как читает видеопроход и как пишут записи: отсчёт i на столбце 2i, фильтр [1 2 1]/4 по столбцам 2i−1…2i+1 и среднее двух строк. Файл помечается `chroma_location=left` явно (и записи тоже).
- **Кодек экспорта** — первый из того же порядка, что прошёл самопроверку и открылся на размере экспорта; проверки скорости нет (экспорт может идти медленнее реального времени).
- **Качество** — постоянное качество кодека: x264 crf 20/25/30, NVENC cq 21/26/31, QSV global_quality 21/26/31, AMF cqp 21/26/31, MF quality 80/60/40 (высокое = как у записи). На тестовой картинке 320×180 x264 даёт 108/256/435 КБ, MF — 454/704/950 КБ за 30 кадров.
- **Превью = экспорт.** Кадр файла, раскодированный и нарисованный видеопроходом, против кадра `Compositor` того же момента: ꟻLIP среднее 0,022–0,034, 99 % ≤ 0,19–0,22 (NVENC, высокое качество; почти всё — шумовой блок testsrc2). Кадр на 0,5 с в сторону даёт среднее ≥ 0,10, 99 % ≥ 0,98 — порог экспорта (0,05 / 0,3) его ловит.

## Задача 5.13: GIF (2026-10-29)

- gifski 1.34 без своего CLI (`default-features = false`, только `gifsicle`): кадры `Compositor` читаются в RGBA (`Gpu::read`) и отдаются `Collector`, квантование и запись идут на потоках gifski, пока рисуются следующие кадры. Для его API нужны крейты `imgref` и `rgb` (типы кадра) — те же версии, что у самого gifski.
- Качество 90 из 100 (у gifski полезно 50–100). Зацикливание: блок NETSCAPE2.0 со счётом 0 (бесконечно); без зацикливания блока нет — плееры играют один раз.
- Замер: синтетика 640×360, 20 fps, 2,5 с — 1,0 МБ; кадр GIF против превью: ꟻLIP среднее 0,020, 99 % ≤ 0,107.
