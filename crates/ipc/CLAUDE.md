# dc-ipc (`crates/ipc`)

Связь процессов devcast между собой и с редактором: local socket (interprocess 2.4; на Windows — именованный канал), сообщения JSON с длиной.

## Инварианты

- Сообщение — длина u32 little-endian + JSON, не больше `MAX_MESSAGE` (16 МиБ); одно подключение — один запрос и один ответ.
- Имя канала — `socket_name(service)` = `devcast-<service>-<пользователь>`: два пользователя одной машины не мешают друг другу.
- Слушатель на имени один: второй `Listener::bind` — `IpcError::Taken`. Никто не слушает — `request` сразу даёт `IpcError::NotRunning` (решение 011: < 0,1 мс).
- Поток в `accept` будит `Listener::wake` (подключиться и сразу закрыть); без ожиданий и опросов.
- Типы сообщений задаёт тот, кто говорит: управление записью — `dc-cli` (`record.rs`), команды редактору — задача 7.32. Если редактор держит проект, CLI пишет только через него.

## Как тестировать

- `cargo nextest run -p dc-ipc`: кадрирование сообщений и настоящий канал с уникальным именем на процесс теста.

## Куда не лезть

- Что делать с сообщением — у отправителя и получателя (`dc-cli`, `dc-app`).
